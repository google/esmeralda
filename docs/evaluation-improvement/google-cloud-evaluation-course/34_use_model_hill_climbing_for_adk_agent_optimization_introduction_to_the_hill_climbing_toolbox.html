Introduction to the hill climbing toolbox

In this lesson, you'll learn the six layers you can modify in generative and agentic systems, and the rule that governs when to target each layer. The different changes you can make to these layers are your toolbox, and diagnosis is how you select the correct layer and tool.

First, you'll walk through the six layers, from the core model up to the user experience. Then, you'll learn why you must diagnose before making adjustments, and how diagnosis is a key part of effective hill climbing hypotheses.
The six hill climbing layers
When you decide to change a generative or agentic system, that change happens in a specific layer in the system. The hill climbing toolbox is organized around the six layers commonly present in generative and agentic systems.
Model layer
Prompt layer
Tool and skill layer
Framework and context layer
Agent design layer
System and UX layer
These layers are not ranked. A model swap and a UX change can be both legitimate mitigations, and the right one depends entirely on what's failing. Which layer you touch on a given pass comes from diagnosis, not preference.

The bulk of this course is organized by layer: model and prompt in Module 3, tools and skills in Module 4, framework and context in Module 5, and agent design and the surrounding system in Module 6.
Diagnosis as the central activity
The most important rule in this course is simple: diagnose before you adjust anything. Every layer in the toolbox is tempting. However, a change made without knowing the cause is a guess, and a guess can cause a hard-to-debug regression.

Blind tweaks often cause regressions because a generative or agentic system has many interacting parts. A prompt edit that fixes one failure can break something else. A model swap that raises quality can exceed your latency budget. When you change a system without a diagnosis, your are more likely to be trading a visible problem for an invisible one. You may be fixing a symptom, but the root cause lives in a different layer and the failure will then manifest in a different form.

Diagnosis is finding the "why." It's the work of locating where a system fails and understanding the mechanism behind the failure. Only once you know the "why" can you write a real hypothesis. Your hypothesis is the "if I change X, then metric A improves, because..." statement. Diagnosis supplies the "because." Without the "because", the hypothesis you formulate is a wish, not an educated guess.
