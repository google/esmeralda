Optimization has no console launch page. It runs through the SDK and ADK tooling, and the optimizer iteratively refines the agent against your test suite. The console role is limited to identifying the inputs. You open the failing run, and its metrics and test cases are what the optimizer improves against.

Warning:

Optimization runs from the SDK and ADK tooling, not a console page. Don’t look for a launch button in the evaluation report. Seed the run from there and launch it programmatically.

Verify the fix by re-running the same evaluation

Run the optimized agent against the same suite, not a fresh one, so before-and-after scores are directly comparable. Track all metrics together. A fix can lift one score while it quietly degrades another, and a single re-run on the shared suite is what makes that trade-off visible.

Improvement is not guaranteed on every Quality Flywheel Lap. This evaluate-and-optimize loop is a form of hill climbing, so a refinement can overfit your eval set or stall at a local peak. Treat each lap as a hypothesis the re-run has to confirm, and rely on the held suite to catch a change that looks better but isn’t. The dedicated hill climbing course covers these dynamics in depth.

Tip: Re-use the exact suite that seeded optimization for the verification run. A different suite makes the before-and-after comparison meaningless.
