The centralized gateway architecture

Scenario generation can help you generate synthetic eval cases. It reads the agent’s instructions and tool definitions, then writes candidate cases that exercise what the agent is built to do. Your first suite reflects the agent’s real capabilities, not only the scenarios you happen to think of.

You start it from the Simulate sessions option in a new experiment. The Traces and Sessions options instead grade data you already have. Its key input is the generation guidance, a short description of the behaviors and edge cases you want covered. Scenario generation then returns a table of candidate cases to review.

The centralized gateway architecture

A simulation run needs a fixed target, so that results are reproducible and two runs are comparable. That target is an agent version in the Agent Registry. It is the instructions, tools, and model frozen together as an immutable snapshot.

You need at least one registered agent version before simulation runs, since the evaluation targets that snapshot. Changing the agent later creates a new version. That new version lets you compare it to an earlier version on the same cases.

The centralized gateway architecture

Each generated case is a specification, not a finished test. It pairs a starting prompt with a conversation plan. The starting prompt is the first message the agent sees. The conversation plan is a hidden instruction that tells the simulated user how to behave for the rest of the conversation. The agent reacts to the starting prompt, and the conversation plan keeps a multi-turn case playing out consistently.

The generated cases can be viewed in a table, where you can edit a prompt, adjust a conversation plan, or add your own cases manually. This is how you can target specific behaviors, such as an ambiguous request or a hard follow-up.
